本文记录从源码编译 Linux 内核的通用流程：获取源码 → 配置 → 编译，不涉及安装与启动。流程适用于各发行版，文中以 Ubuntu 22.04（x86_64）为例演示。

## 1. 获取内核源码

### 方式一：git

直接 clone kernel.org 速度会很慢甚至超时，用镜像快很多：
```bash
# 国内镜像（清华，速度快），但会拉取全量历史（数 GB）
git clone https://mirrors.tuna.tsinghua.edu.cn/git/linux.git

# 只 clone v5.15 标签，不拉全部历史，体积小很多
git clone --branch v5.15 --depth 1 \
  https://mirrors.tuna.tsinghua.edu.cn/git/linux.git
```

+ `--depth 1`（浅克隆）: 表示只取最新一层快照，大幅减小体积、加快下载
    > 代价：本地只有 1 条提交记录（`git log` 仅能看到这一条），也不能切换到其他分支或版本。
    {: .prompt-info }

+ 补充：如果之后想看完整历史，可以补全：
```bash
git fetch --unshallow
```
但对编译内核来说，浅克隆就够了，没必要补全。

### 方式二：压缩包（推荐）

内核源代码 tar 压缩包：[kernel.org 源码目录](https://www.kernel.org/pub/linux/kernel/)
> 进入后按版本（如 `v5.x/`）找到对应的 `.tar.xz` 等压缩包下载。
{: .prompt-info }

下载后解压：
```bash
tar xvf linux-x.y.z.tar.xz
```
+ 现代 tar 会自动识别压缩格式，`.tar.gz`、`.tar.bz2`、`.tar.xz` 都用这一条命令即可；旧式写法中按格式附加的 `z`/`j`/`J` 参数（分别对应 gz/bz2/xz）可以省略。
+ `v` 代表 verbose，显示解压过程，省略后不会显示解压过程。
+ `-C <target_dir>` 代表解压到指定目录，省略后默认解压到当前目录。

## 2. 配置内核

编译前必须先配置内核，决定将哪些功能和驱动程序编译进内核。

配置的结果最终保存在内核源码根目录下的 **`.config`** 文件中，它是内核编译的核心配置文件。

+ `.config` 是一个纯文本文件（以 `.` 开头，默认隐藏），里面是成千上万条形如 `CONFIG_XXX` 的配置项，每一项决定某个功能或驱动是否编译、以何种方式编译。
+ 每个配置项有三种状态：

```text
CONFIG_EXT4_FS=y                 # y：直接编译进内核镜像（built-in）
CONFIG_USB_STORAGE=m             # m：编译成可加载模块（.ko），需要时再加载
# CONFIG_DEBUG_INFO is not set   # 未设置：不编译该功能
```

+ 这个文件通常通过 `make menuconfig`、`make defconfig`、`make oldconfig` 等命令生成和修改（下文介绍）。

> 生成 `.config` 后若还想修改，除了 `make xxxconfig` 命令，也可以直接用编辑器改 `.config` 后编译；或用源码自带的 `scripts/config` 脚本工具修改（如 `scripts/config --disable DEBUG_INFO`），改完执行 `make olddefconfig` 同步即可。
{: .prompt-tip }

> `.config` 决定了最终内核"长什么样"：包含哪些驱动、支持哪些文件系统、开启哪些特性。同一份源码，不同的 `.config` 会编译出功能差异很大的内核。
{: .prompt-info }

### 2.1 准备依赖

配置命令本身也要先编译出 Kconfig 工具才能运行，因此配置阶段需要基础工具链和以下依赖：
```bash
sudo apt install build-essential libncurses-dev bison flex
```
+ `build-essential`：gcc、make 等基础工具链（配置和编译阶段都需要）
+ `libncurses-dev`：`make menuconfig` 图形菜单所需的库
+ `bison` / `flex`：Kconfig 语法解析器的生成工具

**以下方式按情况择一使用：**

### 2.2 生成默认配置

为当前体系结构生成一份默认配置：
```bash
# 进入内核源码目录
cd linux-x.y.z
make defconfig
```


<details markdown="1">
<summary>📖 展开：make defconfig 的工作原理</summary>

**默认配置从哪来？**

`make defconfig` 并非凭空生成配置，而是读取内核源码中**预先定义好的 defconfig 文件**，路径由架构决定：

| 架构 | 默认 defconfig 文件 |
| --- | --- |
| x86 (64位) | `arch/x86/configs/x86_64_defconfig` |
| x86 (32位) | `arch/x86/configs/i386_defconfig` |
| ARM64 | `arch/arm64/configs/defconfig` |
| ARM | `arch/arm/configs/xxx_defconfig`（众多板级配置） |

具体用哪个，由 `arch/<arch>/Makefile` 中的 `KBUILD_DEFCONFIG` 变量决定（如 x86_64 对应 `x86_64_defconfig`）。

**底层做了什么？**

最终调用 `scripts/kconfig/conf` 程序，以 `--defconfig=arch/<arch>/configs/xxx_defconfig` 读取该文件，再结合整棵 Kconfig 规则树，生成完整的 `.config`。

**几个关键认识：**

+ defconfig 文件由**内核 / 板级维护者精心挑选**并提交到源码树，目标是提供一个"最小但能启动"的基础配置，供用户在此基础上定制。
+ defconfig 只包含**显式设置的选项**，并非完整 `.config`；未列出的选项取 Kconfig 中定义的 `default` 值。
+ `make savedefconfig` 可反过来从当前 `.config` 生成一份精简的 defconfig 文件。

</details>


### 2.3 继承原有配置（推荐）
> 给 Ubuntu/Debian 等发行版更换内核的场景非常合适；

1. 解压内核源码，并进入源码目录：

   ```bash
   # 进入内核源码目录
   cd linux-x.y.z
   ```

2. 导入你当前系统正在运行的内核配置：

   Ubuntu/Debian 系统通常会把内核配置文件放在 /boot 目录下，例如：

   ```bash
   # uname -r -> 当前内核版本
   cp /boot/config-$(uname -r) .config
   ```

   这一步就是“用上系统当前的配置”。

3. 根据系统当前配置，生成新的配置。

   两个命令都会读取新源码根目录下的 .config（刚复制过来的）、对照 Kconfig、保留已设置的选项并写回更新后的 .config，唯一区别是**新增选项**的处理方式：

   + `make oldconfig`：逐个询问新选项，让你手动选择（y/n/m）；
   + `make olddefconfig`：新选项自动取默认值，全程无交互（推荐）。

   ```bash
   make olddefconfig
   ```

### 2.4 交互式配置
```bash
make menuconfig
```

#### 2.4.1 交互式配置示例
比如你选中了 CONFIG_SMP 选项后按 h，会显示类似这样的内容：
```
Symbol: SMP [=y]
Type  : bool
Prompt: Symmetric multi-processing support
  Location:
    -> General setup
  Defined at init/Kconfig:88
  Depends on: ...
  Selects: ...
```
+ Symbol: 配置符号名
+ Type: 配置类型（bool/tristate/int/string 等）
+ Prompt: 配置项的描述
+ Location: 配置项在 Kconfig 树中的位置
+ Defined at: 配置项定义的 Kconfig 文件和行号
+ Depends on: 依赖关系（哪些选项必须启用才能启用该选项）
+ Selects: 选择关系（启用该选项会自动启用哪些选项）
{: .text-muted}

**常用快捷键**

| 按键 | 功能 |
| --- | --- |
| `h` | 查看当前选项帮助 |
| `?` | 显示主帮助菜单 |
| `/` | 搜索配置项（输入关键词，如 `EXT4`） |
| `y` / `n` / `m` | 设置当前选项为 是/否/模块 |
| `Enter` | 进入子菜单 / 切换 bool 选项 |
| `Esc` | 返回上级菜单 |
| `Space` | 切换选项状态 |

搜索功能（`/`）特别实用，因为选项数量庞大，直接找几乎不可能。比如输入 GDB_SCRIPTS，它会告诉你这个选项在哪里、是否可选、依赖什么。

## 3. 编译

### 3.1 编译前准备

以 Ubuntu 22.04（默认内核为 5.15 系列）为例，全新系统上直接执行 `make -j$(nproc)` 会不断报缺少依赖的错误，例如：
```text
 CC      /home/zlj/Codes/linux-5.15.1/tools/bpf/resolve_btfids/main.o
main.c:55:10: fatal error: libelf.h: No such file or directory
   55 | #include <libelf.h>
      |          ^~~~~~~~~~
compilation terminated.
```

这些是编译阶段所需的依赖，建议编译前先装好：
```bash
sudo apt install libelf-dev libmpc-dev libgmp-dev libssl-dev
```
+ `libelf-dev`：ELF 解析库，resolve_btfids、objtool 等内核自带工具需要
+ `libssl-dev`：OpenSSL 头文件，模块签名等需要
+ `libmpc-dev` / `libgmp-dev`：GCC 插件所需的数学库

### 3.2 执行编译

.config 配置生成后，编译：
```bash
make -j$(nproc)
```
> `$(nproc)` 值即 逻辑核心数，也即 "物理核心数 x 每核线程数"；
{: .prompt-info }

## 4. 额外知识补充

### 4.1 物理核心数与逻辑核心数

#### 4.1.1 物理核心数
物理核心（Cores）：实际的物理计算单元，决定了 真正的并行计算能力。

- 每个核心都是一个独立的处理单元，能够独立执行指令流。
- 例如，一个 4 核 CPU，理论上可以同时处理 4 个独立的任务。

##### 4.1.1.1 查看物理核心数

```bash
lscpu | grep -E "^Socket\(s\)|^Core\(s\) per socket"
```
- `Socket(s)`：CPU 插槽数（物理 CPU 数量）
  + 主板上实际插了几颗 CPU 芯片。普通台式机/笔记本几乎永远是 1；服务器常见 2 颗（双路），高端的有 4 路、8 路。
- `Core(s) per socket`：每个 CPU 插槽的核心数
  + 一颗芯片内部集成了几个独立的物理计算单元。比如一颗 8 核芯片，Core(s) per socket = 8。
- 物理核心总数 = Socket(s) × Core(s) per socket

**例如输出**：
```
Socket(s):           1
Core(s) per socket:  8
```
说明这台机器有 1 颗 CPU，每颗 8 核，物理核心共 8 个。

##### 4.1.1.2 核心数对系统性能的影响

- **影响多任务处理能力**：
    - 核心数越多，CPU 理论上能同时运行的计算任务（并行计算）就越多，适用于多线程应用（如视频编码、科学计算）。
    - 但如果应用程序 **不支持多线程**，那么即使核心数再多，也不会有明显性能提升。
- **影响系统负载承受能力**：平均负载（Load Average）分析时，核心数影响系统的“饱和点”（按逻辑核心数衡量）：
    - 4 个逻辑核心的 CPU，`Load Average = 4.0` 表示满载但不超载。
    - 8 个逻辑核心的 CPU，`Load Average = 4.0` 说明还有一半的资源空闲。
- **影响 CPU 调度策略**：
    - 多核心可以让更多线程并行执行，减少上下文切换的开销，提高系统吞吐量。
    - 但如果线程数远超核心数，可能会因为 CPU 频繁切换线程（Context Switch）而带来额外开销。

#### 4.1.2 逻辑核心数
逻辑核心（Logical Cores）：操作系统实际看到并调度的执行单元数量，由 物理核心 + 超线程技术（SMT） 共同决定。

- 超线程技术（Intel 称 Hyper-Threading，AMD 称 SMT）让一个物理核心对外呈现为多个逻辑核心，每个逻辑核心都能独立执行指令流。
- 但同一物理核心上的多个逻辑核心 **共享该核心的执行资源**（运算单元、缓存等），所以逻辑核心不等于真正的并行计算能力。

##### 4.1.2.1 查看逻辑核心数
```bash
lscpu | grep -E "^CPU\(s\):|^Thread\(s\) per core"
```
- `Thread(s) per core`：每个物理核心呈现的逻辑线程数，通常为 1（不支持或未开启超线程）或 2（已开启超线程）。
- `CPU(s)`：逻辑核心总数，即操作系统看到的 CPU 数量。
- 逻辑核心总数 = 物理核心总数 × Thread(s) per core

**例如输出**：
```
CPU(s):              16
Thread(s) per core:  2
```
结合上一节的 8 个物理核心：8 × 2 = 16，说明开启了超线程，每个物理核心呈现为 2 个逻辑核心。

也可以直接用 `nproc` 查看逻辑核心数：
```bash
nproc
```
第 3 节 `make -j$(nproc)` 中的并行数正是取自这里。

##### 4.1.2.2 逻辑核心数对系统性能的影响

- **提升吞吐量而非翻倍算力**：
    - 一个线程因等待内存等原因停顿时，另一个线程可以利用物理核心空闲的执行单元，提高核心利用率。
    - 但两个逻辑核心共享执行资源，计算密集型任务的收益通常只有 20%~30%，远不如增加一个物理核心。
- **是系统调度和负载统计的基准**：
    - 操作系统按逻辑核心数调度线程，`nproc`、`top` 中看到的 CPU 数量都是逻辑核心数。
    - 分析平均负载（Load Average）时，“饱和点”也按逻辑核心数衡量：16 个逻辑核心的机器，`Load Average = 16.0` 才算满载。


### 4.2 清理编译产物

编译会在源码目录产生大量 `.o`、`.ko` 等中间文件（可达数十 GB）。内核提供三个清理命令，按需**择一**使用：

| 命令 | 清理范围 | .config | 典型场景 |
| --- | --- | --- | --- |
| `make clean` | 大部分编译产物（.o、.ko、生成的二进制等） | ✅ 保留 | 保留配置重新编译 |
| `make mrproper` | clean + 配置生成文件（.config、autoconf.h 等） | ❌ 删除 | 完全重新开始 |
| `make distclean` | mrproper + 编辑器备份、补丁残留等 | ❌ 删除 | 清理所有痕迹 |

**更换内核成功后，可以全部清除吗？**

可以。运行中的内核依赖的是安装在 `/boot`（vmlinuz、initrd）和 `/lib/modules/<版本>/` 下的文件，与源码目录无关。确认新内核启动正常后，执行 `make mrproper` 甚至删除整个源码目录都不影响系统：

```bash
rm -rf linux-x.y.z    # 源码包 linux-x.y.z.tar.xz 可保留备用
```

两点注意：

- **别删已安装的内核文件**：`/boot/vmlinuz-*`、`/lib/modules/<版本>/` 不是编译产物，删除会影响系统启动和模块加载。
- **建议先保留一段时间**：旧内核留着，新内核出问题时可在 GRUB 回退；源码和 .config 留着便于日后重编译排查。磁盘紧张时再删无妨。
