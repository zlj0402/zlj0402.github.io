本文记录从源码编译并更换 Linux 内核的通用流程：获取源码 → 配置 → 编译 → 安装并启动。流程适用于各发行版，文中以 Ubuntu 22.04（x86_64）为例演示。

## 1. 获取内核源码

### 方式一：git

直接 clone kernel.org 速度会很慢甚至超时，用镜像快很多：
```bash
# 国内镜像（清华，速度快），但会拉取全量历史（数 GB）
git clone https://mirrors.tuna.tsinghua.edu.cn/git/linux.git

# 只 clone v5.15 标签，不拉全部历史，体积小很多
git clone --branch v5.15 --depth 1 \
  https://mirrors.tuna.tsinghua.edu.cn/git/linux.git
```

+ `--depth 1`（浅克隆）: 表示只取最新一层快照，大幅减小体积、加快下载
    > 代价：本地只有 1 条提交记录（`git log` 仅能看到这一条），也不能切换到其他分支或版本。
    {: .prompt-info }

+ 补充：如果之后想看完整历史，可以补全：
```bash
git fetch --unshallow
```
但对编译内核来说，浅克隆就够了，没必要补全。

### 方式二：压缩包（推荐）

内核源代码 tar 压缩包：[kernel.org 源码目录](https://www.kernel.org/pub/linux/kernel/)
> 进入后按版本（如 `v5.x/`）找到对应的 `.tar.xz` 等压缩包下载。
{: .prompt-info }

下载后解压：
```bash
tar xvf linux-x.y.z.tar.xz
```
+ 现代 tar 会自动识别压缩格式，`.tar.gz`、`.tar.bz2`、`.tar.xz` 都用这一条命令即可；旧式写法中按格式附加的 `z`/`j`/`J` 参数（分别对应 gz/bz2/xz）可以省略。
+ `v` 代表 verbose，显示解压过程，省略后不会显示解压过程。
+ `-C <target_dir>` 代表解压到指定目录，省略后默认解压到当前目录。

## 2. 配置内核

编译前必须先配置内核，决定将哪些功能和驱动程序编译进内核。

配置的结果最终保存在内核源码根目录下的 **`.config`** 文件中，它是内核编译的核心配置文件。

+ `.config` 是一个纯文本文件（以 `.` 开头，默认隐藏），里面是成千上万条形如 `CONFIG_XXX` 的配置项，每一项决定某个功能或驱动是否编译、以何种方式编译。
+ 每个配置项有三种状态：

```text
CONFIG_EXT4_FS=y                 # y：直接编译进内核镜像（built-in）
CONFIG_USB_STORAGE=m             # m：编译成可加载模块（.ko），需要时再加载
# CONFIG_DEBUG_INFO is not set   # 未设置：不编译该功能
```

+ 这个文件通常通过 `make menuconfig`、`make defconfig`、`make oldconfig` 等命令生成和修改（下文介绍）。

> 生成 `.config` 后若还想修改，除了 `make xxxconfig` 命令，也可以直接用编辑器改 `.config` 后编译；或用源码自带的 `scripts/config` 脚本工具修改（如 `scripts/config --disable DEBUG_INFO`），改完执行 `make olddefconfig` 同步即可。
{: .prompt-tip }

> `.config` 决定了最终内核"长什么样"：包含哪些驱动、支持哪些文件系统、开启哪些特性。同一份源码，不同的 `.config` 会编译出功能差异很大的内核。
{: .prompt-info }

### 2.1 准备依赖

配置命令本身也要先编译出 Kconfig 工具才能运行，因此配置阶段需要基础工具链和以下依赖：
```bash
sudo apt install build-essential libncurses-dev bison flex
```
+ `build-essential`：gcc、make 等基础工具链（配置和编译阶段都需要）
+ `libncurses-dev`：`make menuconfig` 图形菜单所需的库
+ `bison` / `flex`：Kconfig 语法解析器的生成工具

**以下方式按情况择一使用：**

### 2.2 生成默认配置

为当前体系结构生成一份默认配置：
```bash
# 进入内核源码目录
cd linux-x.y.z
make defconfig
```


<details markdown="1">
<summary>📖 展开：make defconfig 的工作原理</summary>

**默认配置从哪来？**

`make defconfig` 并非凭空生成配置，而是读取内核源码中**预先定义好的 defconfig 文件**，路径由架构决定：

| 架构 | 默认 defconfig 文件 |
| --- | --- |
| x86 (64位) | `arch/x86/configs/x86_64_defconfig` |
| x86 (32位) | `arch/x86/configs/i386_defconfig` |
| ARM64 | `arch/arm64/configs/defconfig` |
| ARM | `arch/arm/configs/xxx_defconfig`（众多板级配置） |

具体用哪个，由 `arch/<arch>/Makefile` 中的 `KBUILD_DEFCONFIG` 变量决定（如 x86_64 对应 `x86_64_defconfig`）。

**底层做了什么？**

最终调用 `scripts/kconfig/conf` 程序，以 `--defconfig=arch/<arch>/configs/xxx_defconfig` 读取该文件，再结合整棵 Kconfig 规则树，生成完整的 `.config`。

**几个关键认识：**

+ defconfig 文件由**内核 / 板级维护者精心挑选**并提交到源码树，目标是提供一个"最小但能启动"的基础配置，供用户在此基础上定制。
+ defconfig 只包含**显式设置的选项**，并非完整 `.config`；未列出的选项取 Kconfig 中定义的 `default` 值。
+ `make savedefconfig` 可反过来从当前 `.config` 生成一份精简的 defconfig 文件。

</details>


### 2.3 继承原有配置（推荐）
> 给 Ubuntu/Debian 等发行版更换内核的场景非常合适；

1. 解压内核源码，并进入源码目录：

   ```bash
   # 进入内核源码目录
   cd linux-x.y.z
   ```

2. 导入你当前系统正在运行的内核配置：

   Ubuntu/Debian 系统通常会把内核配置文件放在 /boot 目录下，例如：

   ```bash
   # uname -r -> 当前内核版本
   cp /boot/config-$(uname -r) .config
   ```

   这一步就是“用上系统当前的配置”。

3. 根据系统当前配置，生成新的配置。

   两个命令都会读取新源码根目录下的 .config（刚复制过来的）、对照 Kconfig、保留已设置的选项并写回更新后的 .config，唯一区别是**新增选项**的处理方式：

   + `make oldconfig`：逐个询问新选项，让你手动选择（y/n/m）；
   + `make olddefconfig`：新选项自动取默认值，全程无交互（推荐）。

   ```bash
   make olddefconfig
   ```

### 2.4 交互式配置
```bash
make menuconfig
```

#### 2.4.1 交互式配置示例
比如你选中了 CONFIG_SMP 选项后按 h，会显示类似这样的内容：
```
Symbol: SMP [=y]
Type  : bool
Prompt: Symmetric multi-processing support
  Location:
    -> General setup
  Defined at init/Kconfig:88
  Depends on: ...
  Selects: ...
```
+ Symbol: 配置符号名
+ Type: 配置类型（bool/tristate/int/string 等）
+ Prompt: 配置项的描述
+ Location: 配置项在 Kconfig 树中的位置
+ Defined at: 配置项定义的 Kconfig 文件和行号
+ Depends on: 依赖关系（哪些选项必须启用才能启用该选项）
+ Selects: 选择关系（启用该选项会自动启用哪些选项）
{: .text-muted}

**常用快捷键**

| 按键 | 功能 |
| --- | --- |
| `h` | 查看当前选项帮助 |
| `?` | 显示主帮助菜单 |
| `/` | 搜索配置项（输入关键词，如 `EXT4`） |
| `y` / `n` / `m` | 设置当前选项为 是/否/模块 |
| `Enter` | 进入子菜单 / 切换 bool 选项 |
| `Esc` | 返回上级菜单 |
| `Space` | 切换选项状态 |

搜索功能（`/`）特别实用，因为选项数量庞大，直接找几乎不可能。比如输入 GDB_SCRIPTS，它会告诉你这个选项在哪里、是否可选、依赖什么。

## 3. 编译

### 3.1 编译前准备

#### 3.1.1 安装依赖包

以 Ubuntu 22.04（默认内核为 5.15 系列）为例，全新系统上直接执行 `make -j$(nproc)` 会不断报缺少依赖的错误，例如：
```text
 CC      /home/zlj/Codes/linux-5.15.1/tools/bpf/resolve_btfids/main.o
main.c:55:10: fatal error: libelf.h: No such file or directory
   55 | #include <libelf.h>
      |          ^~~~~~~~~~
compilation terminated.
```

这些是编译阶段所需的依赖，建议编译前先装好：
```bash
sudo apt install libelf-dev libmpc-dev libgmp-dev libssl-dev
```
+ `libelf-dev`：ELF 解析库，resolve_btfids、objtool 等内核自带工具需要
+ `libssl-dev`：OpenSSL 头文件，模块签名等需要
+ `libmpc-dev` / `libgmp-dev`：GCC 插件所需的数学库

#### 3.1.2 证书文件缺失

使用 2.3 节继承 Ubuntu/Debian 的 .config 后编译，会在 `certs` 阶段报错：
```text
make[1]: *** No rule to make target 'debian/canonical-certs.pem', needed by 'certs/x509_certificate_list'.  Stop.
make[1]: *** Waiting for unfinished jobs....
  CC      certs/system_keyring.o
make: *** [Makefile:1868: certs] Error 2
```

**原因**：Ubuntu 的 .config 引用了发行版自带的签名证书文件，而原版内核源码里没有这些文件：
```text
CONFIG_SYSTEM_TRUSTED_KEYS="debian/canonical-certs.pem"
CONFIG_SYSTEM_REVOCATION_KEYS="debian/canonical-revoked-certs.pem"
```

这个错误会让编译在 `certs` 阶段就中止，后续模块都没编到，`modules.order` 文件也不会生成。

**这两个配置是干什么的：**

| 配置 | 作用 |
| --- | --- |
| `SYSTEM_TRUSTED_KEYS` | 内置到内核“系统信任密钥环”里的证书，用来**验证内核模块的签名** |
| `SYSTEM_REVOCATION_KEYS` | 已吊销的证书列表 |

它们主要服务于 **Secure Boot（安全启动）+ 模块签名验证** 这套机制：Ubuntu 用它自带的证书给官方内核模块签名，内核加载模块时验证签名，防止加载被篡改的模块。

清空这两项后，自己编译的内核不内置任何信任证书，无法验证用发行版证书签名的外部模块；但本内核编译时生成的模块会自动生成密钥签名，加载不受影响，日常使用基本无感知。

**解决方法**：在内核源码目录清空这两个配置项，再重新编译：
```bash
scripts/config --set-str SYSTEM_TRUSTED_KEYS ""
scripts/config --set-str SYSTEM_REVOCATION_KEYS ""
```

验证配置已清空：
```bash
grep -E "SYSTEM_TRUSTED_KEYS|SYSTEM_REVOCATION_KEYS" .config
```

应该看到：
```text
CONFIG_SYSTEM_TRUSTED_KEYS=""
CONFIG_SYSTEM_REVOCATION_KEYS=""
```

然后再继续编译：`make -j$(nproc)`。

#### 3.1.3 缺少 pahole（BTF 生成失败）

同属 Ubuntu .config 带来的问题：`CONFIG_DEBUG_INFO_BTF=y` 要求生成 BTF（BPF Type Format）调试信息，需要 `pahole` 工具。未安装时编译能进行到末尾，但在 `vmlinux` 链接后报错：
```text
BTF: .tmp_vmlinux.btf: pahole (pahole) is not available
Failed to generate BTF for vmlinux
Try to disable CONFIG_DEBUG_INFO_BTF
make: *** [Makefile:1183: vmlinux] Error 1
```

两种解决方式：

**方式一：关闭 BTF（推荐，学习场景最省事）**

BTF 主要服务于 BPF CO-RE 等高级特性，普通学习编译用不到：
```bash
scripts/config --disable DEBUG_INFO_BTF
make olddefconfig
make -j$(nproc)
```

**方式二：安装 pahole（保留 BTF 功能）**

`pahole` 由 `dwarves` 包提供，装完重新 `make` 即可：
```bash
sudo apt install dwarves
```

> 版本注意：较老的发行版（如 Ubuntu 20.04）自带的 dwarves 版本偏旧（1.15），而生成 BTF 通常需要 pahole ≥ 1.16，装完可能仍报版本过低，这种情况下只能改用方式一。
{: .prompt-warning }

### 3.2 执行编译

`.config` 配置生成后，编译：
```bash
make -j$(nproc)
```
> `$(nproc)` 值即 逻辑核心数，也即 "物理核心数 x 每核线程数"；
{: .prompt-info }

> 完整编译通常需要数十分钟到数小时（取决于机器性能和配置项多少），源码树中的编译产物可达数十 GB（清理方式见 5.3）。
{: .prompt-info }

**编译产物及位置**（后续安装、更换内核会用到）：

| 产物 | 位置 | 用途 |
| --- | --- | --- |
| `bzImage` | `arch/x86/boot/bzImage` | 压缩后的内核镜像，安装后即 `/boot/vmlinuz-<版本>` |
| 模块 `.ko` | 源码树内各驱动目录；经 `make modules_install` 安装到 `/lib/modules/<版本>/` | 可加载模块 |
| `System.map` | 源码根目录 | 内核符号表，调试/排查用，通常装到 `/boot/System.map-<版本>` |
| `.config` | 源码根目录 | 本次编译用的配置，通常装到 `/boot/config-<版本>` |
| `vmlinux` | 源码根目录 | 未压缩、带调试信息的内核 ELF，仅调试用，不参与启动 |
| 设备树 `dtb` | `arch/<arch>/boot/dts/` | 仅 ARM/ARM64 等平台需要，x86 用不到 |

版本号取自源码 `Makefile` 的 `VERSION`/`PATCHLEVEL`/`SUBLEVEL`（如 5.15.1），可用 `make kernelrelease` 查看。安装时最核心的是 `bzImage` + 模块，`System.map`、`.config` 是配套文件。

## 4. 安装新内核

### 4.1 安装内核模块

```bash
sudo make modules_install
```
把编译好的模块 `.ko` 安装到 `/lib/modules/<版本>/`，并生成模块依赖关系（`modules.dep` 等），供系统按需加载。

### 4.2 安装内核

```bash
sudo make install
```
把内核镜像等文件安装到 `/boot/` 并完成引导配置，这一步会自动：
- 复制内核镜像到 `/boot/vmlinuz-<版本>`（`System.map`、`.config` 一并安装）
- 生成 initramfs（`/boot/initrd.img-<版本>`），供早期启动加载驱动
- 更新 GRUB 引导菜单，新内核排在首位

### 4.3 确认安装结果

```bash
# 查看已安装的内核
ls /boot/vmlinuz-*

# 查看 GRUB 配置
grep menuentry /boot/grub/grub.cfg
```

### 4.4 重启进入新内核

```bash
sudo reboot
```
重启后一般会**自动进入新内核**：`make install` 会触发 `update-grub`，新内核被写入启动菜单并排在首位（默认项），菜单超时后自动引导。

只有这两种情况才需要手动选：菜单默认被隐藏想呼出时（开机按住 Shift，UEFI 环境按 Esc），或新内核起不来需要回退旧内核时。

### 4.5 验证当前内核

```bash
uname -r
```

### 4.6 删除旧内核（可选）

确认新内核运行正常后，可以删除不再需要的旧内核，释放 `/boot` 空间。

**发行版安装的内核**（apt 安装的，如 `5.15.0-139-generic`）：

```bash
# 查看已安装的内核包
dpkg --list | grep linux-image

# 删除旧内核
sudo apt remove --purge linux-image-<旧版本号>

# 清理残留的依赖包（linux-modules、linux-headers 等）
sudo apt autoremove --purge

# 更新 GRUB
sudo update-grub
```

**手动编译安装的内核**（如本教程编出的 `5.15.1`）不在 dpkg 管理内，如需删除可手动操作：

```bash
sudo rm /boot/vmlinuz-5.15.1 /boot/initrd.img-5.15.1 \
        /boot/System.map-5.15.1 /boot/config-5.15.1
sudo rm -rf /lib/modules/5.15.1
sudo update-grub
```

> 注意：不要删除当前正在运行的内核，并至少保留上一版本，新内核出问题时才能回退。
{: .prompt-warning }

## 5. 扩展

### 5.1 概念补充

#### 5.1.1 物理核心数
物理核心（Cores）：实际的物理计算单元，决定了真正的并行计算能力。

- 每个核心都是一个独立的处理单元，能够独立执行指令流。
- 例如，一个 4 核 CPU，理论上可以同时处理 4 个独立的任务。

##### 5.1.1.1 查看物理核心数

```bash
lscpu | grep -E "^Socket\(s\)|^Core\(s\) per socket"
```
- `Socket(s)`：CPU 插槽数（物理 CPU 数量）
  + 主板上实际插了几颗 CPU 芯片。普通台式机/笔记本几乎永远是 1；服务器常见 2 颗（双路），高端的有 4 路、8 路。
- `Core(s) per socket`：每个 CPU 插槽的核心数
  + 一颗芯片内部集成了几个独立的物理计算单元。比如一颗 8 核芯片，Core(s) per socket = 8。
- 物理核心总数 = Socket(s) × Core(s) per socket

**例如输出**：
```
Socket(s):           1
Core(s) per socket:  8
```
说明这台机器有 1 颗 CPU，每颗 8 核，物理核心共 8 个。

##### 5.1.1.2 核心数对系统性能的影响

- **影响多任务处理能力**：
  + 核心数越多，CPU 理论上能同时运行的计算任务（并行计算）就越多，适用于多线程应用（如视频编码、科学计算）。
  + 但如果应用程序 **不支持多线程**，那么即使核心数再多，也不会有明显性能提升。
- **影响系统负载承受能力**：平均负载（Load Average）分析时，核心数影响系统的“饱和点”（按逻辑核心数衡量）：
  + 4 个逻辑核心的 CPU，`Load Average = 4.0` 表示满载但不超载。
  + 8 个逻辑核心的 CPU，`Load Average = 4.0` 说明还有一半的资源空闲。
- **影响 CPU 调度策略**：
  + 多核心可以让更多线程并行执行，减少上下文切换的开销，提高系统吞吐量。
  + 但如果线程数远超核心数，可能会因为 CPU 频繁切换线程（Context Switch）而带来额外开销。

#### 5.1.2 逻辑核心数
逻辑核心（Logical Cores）：操作系统实际看到并调度的执行单元数量，由物理核心 + 超线程技术（SMT）共同决定。

- 超线程技术（Intel 称 Hyper-Threading，AMD 称 SMT）让一个物理核心对外呈现为多个逻辑核心，每个逻辑核心都能独立执行指令流。
- 但同一物理核心上的多个逻辑核心 **共享该核心的执行资源**（运算单元、缓存等），所以逻辑核心不等于真正的并行计算能力。

##### 5.1.2.1 查看逻辑核心数
```bash
lscpu | grep -E "^CPU\(s\):|^Thread\(s\) per core"
```
- `Thread(s) per core`：每个物理核心呈现的逻辑线程数，通常为 1（不支持或未开启超线程）或 2（已开启超线程）。
- `CPU(s)`：逻辑核心总数，即操作系统看到的 CPU 数量。
- 逻辑核心总数 = 物理核心总数 × Thread(s) per core

**例如输出**：
```
CPU(s):              16
Thread(s) per core:  2
```
结合上一节的 8 个物理核心：8 × 2 = 16，说明开启了超线程，每个物理核心呈现为 2 个逻辑核心。

也可以直接用 `nproc` 查看逻辑核心数：
```bash
nproc
```
3.2 节 `make -j$(nproc)` 中的并行数正是取自这里。

##### 5.1.2.2 逻辑核心数对系统性能的影响

- **提升吞吐量而非翻倍算力**：
  + 一个线程因等待内存等原因停顿时，另一个线程可以利用物理核心空闲的执行单元，提高核心利用率。
  + 但两个逻辑核心共享执行资源，计算密集型任务的收益通常只有 20%~30%，远不如增加一个物理核心。
- **是系统调度和负载统计的基准**：
  + 操作系统按逻辑核心数调度线程，`nproc`、`top` 中看到的 CPU 数量都是逻辑核心数。
  + 分析平均负载（Load Average）时，“饱和点”也按逻辑核心数衡量：16 个逻辑核心的机器，`Load Average = 16.0` 才算满载。

#### 5.1.3 BTF（BPF Type Format）

BTF 是一份描述内核数据类型的“元数据”：把结构体、枚举、typedef、函数签名等类型信息以紧凑格式记录下来，嵌入内核镜像（vmlinux）和模块里。

**解决什么问题**：内核结构体（如 `task_struct`、`sk_buff`）的字段经常随版本变化，BPF 程序访问字段时需要知道“字段叫什么、偏移多少”。BTF 提供了这份“类型地图”。

**主要用途**：

| 用途 | 说明 |
| --- | --- |
| BPF CO-RE | 让 BPF 程序一次编译、跨内核版本运行，libbpf 靠 BTF 自动适配字段变化 |
| BPF 跟踪 / 可观测性 | `bpftrace`、`bpftool` 等工具靠 BTF 理解内核类型 |
| BTFIDS | 编译时 `BTFIDS vmlinux` 步骤解析 BTF 的类型 ID，供 fentry/fexit 等使用 |

**怎么生成**：

```text
DEBUG_INFO（DWARF 调试信息） --pahole 转换--> BTF --嵌入--> vmlinux 的 .BTF 段
```

这就是 BTF 依赖 `CONFIG_DEBUG_INFO`、需要 pahole 的原因（相关报错见 3.1.3 和 5.2.1）。

**需要保留吗**：

- 要玩 BPF、bpftrace、CO-RE → 保留有意义；
- 只是学习编译内核、写普通驱动/模块 → 用不到，按 3.1.3 方式一关掉完全不影响内核正常运行，还能省内存、加快编译。

### 5.2 可能遇到的问题

#### 5.2.1 编译时内存不足（OOM）

##### 5.2.1.1 现象与原因

编译进行到生成 BTF 时，可能出现进程被系统直接杀死的情况：
```text
Killed
  LD      .tmp_vmlinux.kallsyms1
  KSYMS   .tmp_vmlinux.kallsyms1.S
  AS      .tmp_vmlinux.kallsyms1.S
  LD      .tmp_vmlinux.kallsyms2
  KSYMS   .tmp_vmlinux.kallsyms2.S
  AS      .tmp_vmlinux.kallsyms2.S
  LD      vmlinux
  BTFIDS  vmlinux
FAILED: load BTF from vmlinux: No such file or directory
make: *** [Makefile:1183: vmlinux] Error 255
make: *** Deleting file 'vmlinux'
```

关键在第一行的 `Killed`，原因链是：

```
内存不足 → OOM Killer 杀死 pahole → BTF 未生成 → BTFIDS 加载失败
```

生成 BTF 时，pahole 要处理带完整调试信息（DEBUG_INFO）的 vmlinux（可达数百 MB），内存占用很高。内存（含 swap）不够时，内核的 OOM Killer 会直接杀掉 pahole 进程；BTF 没写进 vmlinux，随后 BTFIDS（resolve_btfids）找不到 BTF 就报错。

注意：这和 3.1.3 不是同一类问题——工具已经装好，只是**跑到一半被系统杀了**，继续装包解决不了。

##### 5.2.1.2 解决方法：加 swap、降并发

```bash
# 新增 4G swap 兜底（若 /swapfile 已存在且在用，换个文件名，否则会报 Text file busy）
sudo fallocate -l 4G /swapfile2
sudo chmod 600 /swapfile2
sudo mkswap /swapfile2
sudo swapon /swapfile2

# 降低并发，减少内存峰值（加 swap 后可选）
make -j2
```

**或者，如果你想直接扩容原来那个（先关掉再重建）：**

```bash
sudo swapoff /swapfile          # 先停用
sudo fallocate -l 4G /swapfile  # 重新分配
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile           # 重新启用
```

+ 加 4G 后仍被 `Killed`，就把 swap 加到 8G，或降到 `make -j1`。
+ 这样添加的 swap 重启后失效；需要永久生效要写进 `/etc/fstab`。仅为临时编译用可以不写。

##### 5.2.1.3 什么是 Swap（交换空间）

Swap 是用硬盘空间充当的“备用内存”，在 RAM 不足时兜底。

**原理**：RAM 快但容量有限。当 RAM 快满时，内核把暂时不活跃的内存页挪到硬盘上的 swap 区，腾出 RAM 给正在干活的进程（如 pahole、链接器），需要时再换回来。

**对编译内核的作用**：链接 vmlinux、生成 BTF 是内存峰值最高的阶段，小内存虚拟机（如 3~4 GB）容易在这一步耗尽内存。加了 swap 后，超出 RAM 的部分溢出到硬盘，进程不被 OOM 杀死，编译能跑完。**swap 不会让编译变快，只是让编译不被杀、能完成。**

**代价**：硬盘比 RAM 慢几个数量级，频繁换入换出（thrashing）会明显拖慢速度；SSD 上影响相对小。慢总比失败强。swap 只是应急兜底，经常编译内核的话，给虚拟机多分配内存才是根本解法。

#### 5.2.2 编译产物架构不对：ARCH 环境变量残留

**现象**：主机明明是 x86_64，编译出的却是 ARM 架构的产物，`.config` 里出现 `CONFIG_ARM=y` 而没有 `CONFIG_X86_64`：

```bash
$ uname -m
x86_64
$ grep -E "^CONFIG_X86_64=|^CONFIG_ARM=" .config
CONFIG_ARM=y
```

**原因**：之前交叉编译时 `export` 过 `ARCH=arm`、`CROSS_COMPILE=arm-linux-gnueabihf-`，变量残留在当前 shell 中。`ARCH` 决定读取哪棵架构 Kconfig 树：

```text
ARCH 未定义 → SUBARCH = uname -m 换算（x86_64 → x86）→ 读 arch/x86/Kconfig
ARCH 已导出 → 直接使用 → 读 arch/arm/Kconfig
```

arm 树里 `config ARM` 是 `default y`，而 x86 的符号（`X86_64` 等）不在树上，于是 `olddefconfig` 生成了一份 ARM 配置。

**排查**：

```bash
echo "ARCH=$ARCH"       # 输出为空表示未设置
env | grep -E "^(ARCH|CROSS_COMPILE)="
```

**解决**：

1. 清除环境变量：
   ```bash
   unset ARCH CROSS_COMPILE
   ```
   必须 `unset`；`export ARCH=""` 置空无效——make 的 `ARCH ?= $(SUBARCH)` 只在变量**未定义**时才回退检测，空值也算已定义。

2. `.config` 已被 ARM 默认值污染，需从头生成：
   ```bash
   make mrproper
   cp /boot/config-$(uname -r) .config
   make olddefconfig
   grep -E "^CONFIG_X86_64=|^CONFIG_ARM=" .config   # 应看到 X86_64=y，无 ARM
   ```

3. 排查是否写进了启动文件（那样新开的终端也会带上）：
   ```bash
   grep -n "ARCH\|CROSS_COMPILE" ~/.bashrc ~/.profile
   ```

交叉编译本身需要这两个变量，正确做法是**只在当次 shell 临时 export**，用完退出该 shell，不要写进 `.bashrc`/`.profile`。本机编译不需要任何环境变量；需要显式指定时可随命令传入：`make ARCH=x86 olddefconfig`。

#### 5.2.3 make install 提示缺少 bzImage

`make install` 只做安装、不负责编译。如果之前的编译没有完整跑完（中途因 OOM、缺少依赖等原因中断），安装步骤会因找不到内核镜像而失败：
```text
 *** Missing file: arch/x86/boot/bzImage
 *** You need to run "make" before "make install".
make: *** [arch/x86/Makefile:262: install] Error 1
```

先补编内核镜像：
```bash
make bzImage -j$(nproc)
```

若接着报缺少 `zstd`：
```text
ZSTD22  arch/x86/boot/compressed/vmlinux.bin.zst
/bin/sh: 1: zstd: not found
make[2]: *** [arch/x86/boot/compressed/Makefile:136: arch/x86/boot/compressed/vmlinux.bin.zst] Error 127
```

那是因为配置选择了用 ZSTD 压缩内核镜像（`CONFIG_KERNEL_ZSTD`，Ubuntu 的 config 默认开启）。装上 zstd 后重新编译：
```bash
sudo apt install zstd
make bzImage -j$(nproc)
```

看到 `Kernel: arch/x86/boot/bzImage is ready` 后，再执行 `sudo make install` 即可正常安装。

> 安装日志开头的 `arch/x86/Makefile:142: CONFIG_X86_X32 enabled but no binutils support` 只是警告：配置启用了 x32 ABI 但工具链不支持，不影响安装和内核使用，可忽略。
{: .prompt-info }

#### 5.2.4 make install 无法完成时，手动安装内核

若 `make install` 因任何原因无法完成，可以手动执行它内部的整套步骤。以版本 5.15.1 为例（用 `make kernelrelease` 获取自己内核的版本号）：

```bash
# 1. 安装内核模块（若 4.1 已执行可跳过）
sudo make modules_install

# 2. 复制内核镜像
sudo cp arch/x86/boot/bzImage /boot/vmlinuz-5.15.1

# 3. 复制符号表与配置文件
sudo cp System.map /boot/System.map-5.15.1
sudo cp .config /boot/config-5.15.1

# 4. 生成 initramfs（-c 创建新的，-k 指定内核版本）
sudo update-initramfs -c -k 5.15.1

# 5. 更新 GRUB 引导菜单
sudo update-grub

# 6. 重启
sudo reboot
```

重启后执行 `uname -r` 应输出 `5.15.1`，即已进入新内核。

### 5.3 清理编译产物

编译会在源码目录产生大量 `.o`、`.ko` 等中间文件（可达数十 GB）。内核提供三个清理命令，按需**择一**使用：

| 命令 | 清理范围 | .config | 典型场景 |
| --- | --- | --- | --- |
| `make clean` | 大部分编译产物（.o、.ko、生成的二进制等） | ✅ 保留 | 保留配置重新编译 |
| `make mrproper` | clean + 配置生成文件（.config、autoconf.h 等） | ❌ 删除 | 完全重新开始 |
| `make distclean` | mrproper + 编辑器备份、补丁残留等 | ❌ 删除 | 清理所有痕迹 |

**更换内核成功后，可以全部清除吗？**

可以。运行中的内核依赖的是安装在 `/boot`（vmlinuz、initrd）和 `/lib/modules/<版本>/` 下的文件，与源码目录无关。确认新内核启动正常后，执行 `make mrproper` 甚至删除整个源码目录都不影响系统：

```bash
rm -rf linux-x.y.z    # 源码包 linux-x.y.z.tar.xz 可保留备用
```

两点注意：

- **别删已安装的内核文件**：`/boot/vmlinuz-*`、`/lib/modules/<版本>/` 不是编译产物，删除会影响系统启动和模块加载。
- **建议先保留一段时间**：旧内核留着，新内核出问题时可在 GRUB 回退；源码和 .config 留着便于日后重编译排查。磁盘紧张时再删无妨。
